$ feature-forge

Um sistema operacional para o desenvolvimento de features mobile — Android, iOS, KMP e Web — com zero ambiguidade.

pressione → para começar  ·  ? para atalhos

01 / 24Abertura

o problema

Toda feature mobile começa do zero.

  • PRD vago. Decisões espalhadas em PRs antigos, Notion, Slack e na cabeça de quem viu primeiro.
  • Ambiguidade vira retrabalho. Dev descobre o que fazer enquanto faz — e três pessoas fazem três coisas diferentes.
  • Quatro plataformas, quatro padrões. Android, iOS, shared (KMP), Web. Cada uma reinventa as mesmas regras.
  • Cada projeto inventa sua skill. Nada portável. Nada absorvível. Conhecimento evapora a cada migração.
02 / 24Abertura · o problema

princípios

6 regras que sustentam o forge.

01 · patterns ≠ deps

Absorve essências de outras skills. Nunca amarra runtime.

02 · files > memory

Tudo file-driven. Inspecionável, retomável, versionável.

03 · o user decide

O engine nunca decide produto, arquitetura ou stack.

04 · mentor calmo

Caloroso na exploração. Firme nos gates.

05 · vocabulário nativo

Lê CLAUDE.md e rules/. Usa as palavras do projeto.

06 · reversibilidade

Toda ação é undo-able. Sem estado oculto.

03 / 24Princípios

o que NÃO é

forge não decide por você.

  • Não é Product Manager. Não decide O QUE a feature faz.
  • Não é arquiteto. Não decide QUAL stack usar.
  • Não é code reviewer. Não decide SE o código é bom.
  • Não é project manager. Não estima, agenda, nem coordena prazos.

Quando perguntam qualquer dessas, redireciona oferecendo o valor adjacente que pode entregar.

04 / 24Princípios · escopo OUT

a interface

13 verbos. Zero flags.

01forge initscan do projeto, propõe cards, escreve config, semeia memória 02forge planpipeline de planning até readiness=ready 03forge implementexecuta 1 task: plan → apply → review → commit
04forge verifyhard gates read-only por task ou feature 05forge statusboard read-only do estado atual 06forge doctorhealth check de config, cards, memória, hooks
07forge reconfigureúnico entrypoint pra qualquer mutação pós-init 08forge graphqueries no graph (similares, blast-radius) 09forge memoryinspeciona e gerencia memória L1–L5
10forge evolverevisa propostas do retrospective-agent 11forge undoreverte a última ação que mudou estado 12forge rawescape hatch pra scripts internos
13 · novo em v1.2forge qagate adversarial red-team — 4 attack vectors × 4 escopos, sandbox isolado, verdict informativo (BLOCK/FLAG/PASS)

100% conversacional. Cada parâmetro é coletado por prompt interativo, dentro de um dos 13.

06 / 24Anatomia · visão geral

L0 · engine core

Uma máquina de estados em arquivos.

  • Ciclo único. plan → apply → verify → commit. Toda operação cabe nele.
  • File-driven. Estado em YAML/JSON no disco. Nada vive só em memória.
  • Resumível. Mata o processo, reabre — continua do checkpoint.
  • Auditável. history.jsonl registra cada transição com timestamp e rationale.
# .claude/state.yaml
feature: register
task: TASK-0003
status: implementing
last_checkpoint: 2026-05-29T14:32:11Z
artifacts:
  - feature-prd.md
  - bdd.md
  - tech-spec.md
  - task-contracts/*.yaml
07 / 24Anatomia · L0 Engine Core

L1 · knowledge substrate

O forge aprende o seu projeto.

  • codebase-graph.db — SQLite vivo (schema v2, 17 queries Q1–Q17 + reuse-intelligence). Responde "onde está X?" em ms.
  • inventory/ — design-system, i18n, conventions em YAML, extraídos automaticamente.
  • memory L1–L5 — do efêmero ao canônico.
L1session · efêmero, esquecido ao fechar
L2project · durável em .claude/memory/
L3user · cross-project, no perfil do usuário
L4card · padrões enviados por capability cards
L5canonical · o repo do feature-forge

Meta: na feature N o questionário é menor que na feature 1.

08 / 24Anatomia · L1 Knowledge

L2 · external integrations

Conectado onde já existe contexto.

ticketing MCP

Lê tickets do Jira, Linear, GitHub Issues. forge plan aceita ID e puxa descrição, anexos, comentários.

docs MCP (Context7)

Docs atualizadas de libs e frameworks. SDK syntax, APIs, breaking changes — sem chutar de memória.

vision

Análise de screenshot. screen-analysis-agent lê o design e gera a especificação visual da tela.

find-skills

Quando um card precisa de capacidade nova (TDD, debug, ship), instala via Skill ecosystem.

09 / 24Anatomia · L2 Integrations

L3 · capability cards

Tudo é composto de cards atômicos.

  • Card = unidade declarativa de capacidade. Provides, requires, conflicts-with, contributes.
  • Preset = alias para uma combinação de cards. Não é estrutura fixa.
  • Add/remove/swap atomicamente. O engine resolve conflitos no init.
  • Portabilidade — funciona em qualquer combinação, mesmo as não previstas.
# cards/koin-annotations/card.yaml
name: koin-annotations
provides: [dependency-injection]
conflicts-with: [hilt-di]
requires: [kotlin-language]
contributes:
  templates:
    - koin-module.kt.tmpl
  validators:
    - no-koin-dsl-in-prod
  agent-prompts:
    - koin-injection-rules.md

11 / 24Anatomia · L4 Orchestration

L5 · self-evolution

O forge sugere. Nunca decide.

  feature termina
        │
        ▼
  retrospective-agent  → detecta padrões repetidos, drift, gaps
        │
        ▼
  proposed-evolutions.yaml  → 16 kinds: patches · cards · regras · reuse
        │
        ▼
  forge evolve  → user revisa, aceita, rejeita ou adia
        │
        ▼
  aplicado · rejeitado · deferido

A engine nunca se modifica sem aprovação. Cada proposta vem com rationale e diff.

13 / 24Fluxo · big picture

forge plan

Cinco waves até readiness = ready.

  • Wave A · intake slug, owner, escopo, ticket
  • Wave B · PRD + screen-analysis paralelo — produto e tela
  • Wave C · contracts data · navigation · analytics · behavior · security
  • Wave D · tech-spec SDD: arquitetura, módulos, estados
  • Wave E · task-contracts + readiness microtarefas executáveis + auditoria final

14 / 24Fluxo · forge plan

subtypes

plan não é só feature nova. É bug, refactor, spike.

  • product — feature nova, 5 waves completas.
  • bugfix — detecta o ticket (IN-37234), pula o PRD, vai ao reparo.
  • refactor — contrato no-behavior-change, gate dedicado.
  • spike · chore — exploração e manutenção, waves enxutas.
$ forge plan bugfix-IN-37234

subtype: bugfix   # detectado pelo ticket
ticket:  IN-37234 · NullPointerException

1. reproduz com regression test   # falha primeiro
2. corrige o mínimo
3. test fica verde
4. 5-whys auto-retro → forge evolve

Bug urgente não pula rigor: o regression test que falha primeiro é hard-gate. Velocidade sem sacrificar a rede de segurança.

15 / 24Fluxo · subtypes

artefatos do plan

Um feature package completo.

feature-prd.md

O que a feature faz. Linguagem de produto, contexto, escopo IN/OUT.

bdd.md

Comportamento em Gherkin. Cada cenário vira teste no shared layer.

screen-analysis.md

Telas faithful ao design. Estados, transições, edge cases visuais.

tech-spec.md

SDD: módulos, estados, fluxos, decisões de arquitetura.

*.contract.yaml

4–5 contratos canônicos: data, nav, analytics, behavior, security.

task-contracts/

Microtarefas executáveis. Cada uma é 1 commit atômico.

Cada arquivo tem schema. Validação programática bloqueia drift.

16 / 24Fluxo · artefatos

forge implement

Uma task. Um commit. Um ciclo.

  ▸ Plan Mode     — agente lê o task-contract, propõe diff. Sem editar nada.
       │
       ▼
  ▸ Apply Mode    — aplica a edição exatamente como planejada.
       │
       ▼
  ▸ Review        — pre-commit-reviewer audita diff vs contrato + gates.
       │
       ▼
  ▸ Commit        — atômico. Mensagem padronizada. Próxima task só depois do verde.

Se algo desvia do contrato, para imediatamente. Sem improviso.

17 / 24Fluxo · forge implement

forge verify

Hard gates. Read-only. Sem improviso.

task-scope

Roda os gates do task-contract: testes, lint, build, diff dentro de allowed_files.

feature-scope

Integração end-to-end: cenários BDD, contratos cumpridos, cobertura, paridade entre plataformas.

inferred-scope

Sem argumento? Detecta automaticamente onde o estado está e roda o escopo apropriado.

Cascade de 20 validators, fail-fast no primeiro erro duro: complexity (CC multi-lang), secrets (gitleaks · trufflehog), no-behavior-change (refactor). A engine nunca muta — só relata pass ou fail com evidências.

18 / 24Fluxo · forge verify

forge qa

Um red-team contra os próprios artefatos.

  • 4 attack vectors spec-vs-spec · chaos · coverage · validator-claim. Inventa cenários hostis.
  • 4 escopos feature · screen · task · paranoid (cross-feature).
  • Sandbox isolado fixtures sintéticos em .planning/qa/<run-id>/ — nunca tocam o repo.
  • Verdict informativo BLOCK · FLAG · PASS. Relata, não bloqueia o commit.
$ forge qa

scope: feature register
vectors: 4 · fixtures: 12   # sandbox isolado

FLAG  spec-vs-spec: nav contract
      contradiz screen-analysis §3
PASS  chaos · coverage · validator-claim

findings → forge evolve

Findings viram propostas em forge evolve. O veredito final continua humano (Decisão 5).

19 / 24Fluxo · forge qa

auto-evolução

Cada feature deixa o forge mais inteligente.

  • retrospective-agent roda automático ao terminar a feature. Lê history.jsonl, commits, gates falhados.
  • Detecta o que repetiu. Padrões em 3+ features viram candidatos a template ou regra.
  • memory-distiller move L1 → L2. O que era achado de sessão vira conhecimento durável de projeto.
  • Propostas vão pra fila. proposed-evolutions.yaml — esperando review humano.
20 / 24Auto-evolução · aprendizado

forge evolve

O controle final é seu.

  • Cada proposta: diff + contexto + rationale + features de origem.
  • Aceitar: aplica patch (template, card, regra, prompt).
  • Rejeitar: vai pra rejected-evolutions.yaml com motivo.
  • Adiar: fica na fila para próxima revisão.
$ forge evolve

3 propostas na fila

[1/3] add validator: detect-koin-dsl
      origem: feat-register, feat-bonsai-form
      aceitar · rejeitar · adiar · ver diff

[2/3] patch template: tech-spec §11.3
      ...

16 kinds — 10 retrospective + 6 reuse-intelligence. Engine sugere, user decide. Sempre.
